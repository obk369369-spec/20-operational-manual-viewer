1. 아래 제I부와 제II부는 별개 작업 지시가 아니다. 원본의 모든 요구를 유지하고 공통 검사·증거·수정은 단 한 번 실행하여 양쪽 조건에 함께 적용한다. 어느 한쪽의 세부 Hard Gate, 테스트, 산출물, 보고 항목도 생략하지 않는다.
2. 실행 장소는 사무실 데스크톱의 Work다. 전날 노트북의 sandbox DNS 오류, network restricted, config.toml network_access=true 미반영, Python 경고, GitHub 연결 문제를 사무실 환경의 사실로 전제하지 않는다. 사무실의 실제 세션 권한과 네트워크를 필요한 범위에서 한 번만 확인한다. 환경이 정상이면 노트북 장애 재현/추가 진단 없이 본 작업에 진입한다.
3. 사무실 환경의 일부 lane만 막혔다면 해당 lane만 BLOCKED로 격리하고, 해당 lane의 필수 Gate를 우회하지 않는 범위에서 독립적으로 가능한 작업은 계속한다. 필수 PRE-WORK HARD GATE가 FAIL인 대상은 운영 본 작업과 FINAL PASS를 금지한다. 단, Gate 통과에 필요한 최소한의 비파괴적 원인 수정과 해당 수정의 검증은 preflight remediation으로 허용한다. 이것을 전체 본 작업 PASS로 오인하지 않는다.
4. 기존 canonical repo, PASS_LOCK, Evidence, Registry, Queue, Backlog, Checkpoint, Golden/Negative Fixture를 재사용한다. 약 3,200건 전수 재검사, 이미 검증된 PASS 재실행, 원본 재업로드 요구, 새 프로그램/새 대화창 남발 금지. 변경된 부분에만 증분·영향기반 검증한다.
5. 제I부의 고정 checkpoint/commit/미완료 수량은 그 당시의 역사적 기준점이지 현재 최신값의 증거가 아니다. 먼저 실제 저장소에서 최신 verified checkpoint, branch/HEAD, 원격 상태, PASS_LOCK 및 NEXT_ROOT를 read-back하고, 일치하지 않으면 기존 자료를 덮어쓰지 말고 충돌을 기록·해결한다. 특히 과거 commit SHA를 무조건 강제 checkout하거나 최신 증거를 되돌리지 않는다.
6. 제II부 A~F는 검증해야 할 선행 원인 후보로 받아들인다. CONFIRMED/REJECTED/ADDITIONAL_ROOT_CAUSE로 기존 증거를 통해 분류하고, 확인된 원인만 실제 구조에서 수정한다. 동일 원인에 대한 분석·수정·테스트·Evidence를 두 번 수행하지 않는다.
7. 원인 조사는 실제 작업 진전과 연결한다. 환경이 허용하면 수정 → 최소 회귀검증 → 실제 최신 입력 FULL PLATFORM E2E 1회 → Negative/Recovery/Restart/False-Pass/Read-back/Observer로 종료한다. 전체 E2E가 실제 원본/권한 부재로 불가능하면 절대 가짜 PASS하지 않고, 실행 가능한 독립 작업의 실제 산출물과 차단된 lane을 분리 기록한다.
8. TOOL013의 actual input, 440건 실데이터 E2E, 원본 XLSX reopen 및 record identity, 24시간 자연시간 검증은 각자의 선행 조건과 범위를 유지한다. 24시간 PENDING을 임의 PASS하거나 자연시간 검증을 다시 시작하지 않는다. 한 작업의 PASS를 전체 WIC의 PASS로 승격하지 않는다.
9. 사용자 역할은 OBSERVER/FINAL APPROVER다. 사용자 반복 설명·복사·재실행은 금지하되, 권한 승인, 외부 원본 부재, 서비스·플랫폼이 허용하지 않는 동작은 실제로 우회했다고 주장하지 말고 명확한 BLOCK 증거와 자동 재개 가능한 체크포인트를 남긴다.
10. Work 크레딧을 환경 진단에 소진하지 않는다. 한 번의 빠른 startup check 후 정상 lane을 바로 실행하고, 중단 전에는 반드시 수정 파일, 실제 산출물, 검증 결과, Evidence, GitHub commit/remote read-back 여부, BLOCK, 정확한 NEXT_ROOT/resume point를 저장한다. 원격 저장이 막히면 로컬 저장과 remote PENDING을 구분한다.
11. 서로 다른 문장 간 해석 충돌 시, (a) 실제 입력·권한·증거 없는 PASS 금지, (b) 원본/기존 PASS 보존, (c) 필수 Gate 우회 금지, (d) 안전한 독립 lane 계속 실행, (e) 중복 실행 최소화 순으로 판단한다. 수행할 수 없는 조건은 완료로 바꾸지 않는다.
12. 이 문서의 제I부와 제II부는 축약본이 아닌 사용자가 제공한 원문 전체이며, 제I부의 구체적 실행·검증 규칙과 제II부의 사무실 환경·선행원인·범위·크레딧 규칙을 모두 강제한다.

============================================================

모든 실제 WIC 업무는 반드시 다음 경로를 통과해야 한다.

INPUT
→ IDENTITY
→ REGISTRY
→ LATEST MASTER
→ CURRENT REQUIREMENTS
→ FEEDBACK HISTORY
→ FAILURE/RECURRENCE HISTORY
→ REQUIRED DATA
→ EXECUTION
→ AUTO-RECOVERY WHEN REQUIRED
→ ROW ISOLATION WHEN REQUIRED
→ VALIDATOR
→ INDEPENDENT/EXTERNAL VALIDATION WHEN REQUIRED
→ EVIDENCE
→ COMPLETION MATH
→ REGRESSION
→ READ-BACK
→ OUTPUT GATE
→ FINAL OUTPUT
→ OBSERVER REPORT

이 경로 중 필수 Gate를 건너뛰어도
최종 결과가 생성되는 BYPASS가 단 하나라도 발견되면:

ZERO_RECURRENCE_GATE = FAIL

본 작업의 FINAL PASS를 금지한다.

라고 정의하지 않는다.

목표는 다음이다.

ERROR MAY OCCUR

BUT

UNDETECTED ERROR → FINAL PASS = FORBIDDEN


행 단위로 안전하게 처리 가능한 오류는:

ERROR
→ DETECT
→ CLASSIFY
→ AUTO-REPAIR
→ RETEST
→ PASS RECORD

또는

ERROR
→ DETECT
→ CLASSIFY
→ AUTO-REPAIR ATTEMPT
→ UNRESOLVED
→ QUARANTINE RECORD
→ CONTINUE OTHER SAFE RECORDS

둘 중 하나로 처리한다.


그러나 record identity 자체가 신뢰할 수 없는 경우:

IDENTITY ERROR
→ DETECT
→ BLOCK AFFECTED OUTPUT
→ HOLD

한다.


다음 경로는 금지한다.

ERROR
→ UNDETECTED
→ PASS

ERROR
→ USER MANUAL MASS REPAIR
→ PASS

ONE BAD ROW
→ BLOCK ALL OTHERWISE SAFE ROWS

경로는 0개여야 한다.

UNRESOLVED

그리고 다음 불변식을 검사한다.

TOTAL =
FINAL_USABLE
+ QUARANTINED
+ 명시적으로 허용된 기타 최종상태

숫자가 맞지 않으면 OUTPUT BLOCK.

이번 행 처리 작업에서는 특히:

INPUT_RECORD_COUNT
NORMAL_RECORD_COUNT
AUTO_REPAIRED_COUNT
QUARANTINED_COUNT
FINAL_USABLE_COUNT

MISSING_RECORD_COUNT
DUPLICATE_RECORD_COUNT
IDENTITY_SWAP_COUNT
CROSS_ROW_MIX_COUNT

를 반드시 계산한다.

그리고:

INPUT_RECORD_COUNT
=
FINAL_USABLE_COUNT
+
QUARANTINED_COUNT
+
명시적으로 허용된 비업무 record

관계를 증명한다.

검증완료가 필수인 업무에서

VALIDATED != 검증대상 TOTAL

이면 FINAL PASS 금지.

따라서 다시는

51건 중 9건 검증
→ 51건 완료본 생성

같은 경로를 허용하지 않는다.

동시에:

1,000행 중 5행 문제
→ 1,000행 전체 사용불가

도 자동적으로 허용하지 않는다.

identity가 안전하다면:

980 정상
+ 15 자동수정
+ 5 격리
=
995 사용가능
+ 5 격리

형태가 되어야 한다.


============================================================
4. FIELD-LEVEL EVIDENCE LOCK
============================================================

문서 전체에 PASS 하나만 붙이지 않는다.

필수 필드마다:

ORIGINAL_VALUE
VALIDATED_VALUE
SOURCE
EVIDENCE
VALIDATION_METHOD
STATUS

를 연결한다.

자동수정된 필드에는 추가로:

AUTO_REPAIR_METHOD
BEFORE_VALUE
AFTER_VALUE
REVALIDATION_STATUS

를 연결한다.

필수 필드 중 하나라도 Evidence가 없으면
해당 Record의 FINAL PASS를 차단한다.

그러나 독립 record 하나의 field 실패를
다른 안전한 record의 실패로 전파하지 않는다.

Record-level failure와
Batch-level identity corruption을 구분한다.


============================================================
5. 동일 오류 재발 차단
============================================================

모든 Failure에 ROOT_FINGERPRINT를 만든다.

새 오류 발생 시:

NEW FAILURE
→ EXISTING ROOT SEARCH
→ SAME ROOT?
   YES → RECURRENCE
   NO → NEW ROOT

동일 Root의 Recurrence가 발생하면
단순히 그 한 건만 다시 고치지 않는다.

OLD PASS INVALIDATE
→ ROOT REOPEN
→ 왜 기존 Validator가 막지 못했는지 조사
→ Validator/Enforcement 수정
→ 기존 Negative Fixture 추가
→ RED TEST
→ FIX
→ GREEN TEST
→ REGRESSION
→ NEW PASS

동일 Root Cause가 사용자에게 다시 발견되면
기존 구조의 FINAL PASS는 잘못된 것으로 간주한다.

이번 TOOL013 사용자 실제 결과는
Negative Golden으로 유지한다.

RECORD_IDENTITY_INTEGRITY_UNPROVEN

CATEGORY_CODE_AS_DISPLAY_VALUE

WRONG_COLUMN_MAPPING

BLANK_REQUIRED_OUTPUT

DUPLICATE_RECORD

MISSING_RECORD

OUTPUT_NOT_REOPENED

← OUTPUT GATE
← COMPLETION MATH
← VALIDATOR
← EVIDENCE
← EXECUTION
← REQUIREMENTS
← MASTER
← REGISTRY
← IDENTITY
← INPUT

을 역방향으로 추적한다.

각 핵심 결과가 원본까지 추적되지 않으면 FAIL.

각 최종 record도:

FINAL RECORD
← stable_record_id
← origin_row
← origin_file

까지 추적되어야 한다.

16. FALSE-PASS ATTACK
============================================================

FINAL PASS 직전에 시스템 스스로 다음 질문으로
자기 완료판정을 공격한다.

"어떤 방법으로 아직 미완료인데도
이 결과가 PASS될 수 있는가?"

가능한 우회경로를 탐색한다.

하나라도 발견하면
FINAL PASS를 취소하고 Root를 OPEN한다.

다음도 공격한다.

- 일부 항목 누락
- Evidence 삭제
- 오래된 Master
- 오래된 Runtime
- Registry 누락
- Validator 미실행
- External validation 실패
- 저장 실패
- Read-back 실패
- 중간 실행 중단
- 동일 오류 recurrence
- 잘못된 target routing
- stale state
- fixture만 성공
- 보고만 성공
- 실행은 성공했으나 전달 실패
- 문제행 때문에 정상행 전체가 차단됨
- deterministic 오류가 사용자에게 전달됨
- correction workbook이 사용자 작업지시서가 됨
- identity 누락
- duplicate
- identity swap
- cross-row mixing
- 실제 XLSX를 reopen하지 않음
- 내부 객체만 정상이고 실제 파일은 잘못됨

위 상황에서 잘못된 FINAL PASS가 하나라도 가능하면 FAIL.

원인 B — 실제 입력이 연결되지 않았는데 상위 PASS가 만들어진 사례
------------------------------------------------------------

기존 감사 과정에서

actual_wic_input = null

또는 증분 Evidence MISSING 등 실제 입력/증거 문제가 있는데도
상위 PASS와 실제 하위 상태가 완전히 일치하지 않는 사례가 있었다.

하위에

OPEN
HOLD
PARTIAL
RETEST_REQUIRED

등이 존재하는데도 상위 PASS가 만들어질 수 있었다면,
기존 완료 차단장치가 하위 실제 상태와 상위 PASS를
완전히 묶지 못했다는 뜻이다.

ROOT PASS를 별도의 선언값으로 임의 생성하지 못하게 하라.

ROOT PASS는 반드시 실제 하위 상태와 Evidence로부터 계산되어야 한다.

하위 상태와 모순되는 ROOT PASS는 구조적으로 생성 불가능해야 한다.


------------------------------------------------------------
원인 C — 실행환경 실패와 업무 실패가 섞였다
------------------------------------------------------------

최근 실행에서는

WINDOWS_SANDBOX_HELPER_SETUP_REFRESH_ERROR

등 실행환경 문제가 발생했다.

또 어떤 실행에서는

Codex
Node
Python
GitHub

접근 자체는 가능했더라도
LOCAL HEAD와 원격 CENTRAL 상태 차이 등의 이유로
CENTRAL resume 또는 PRE-WORK HARD GATE가 차단되는 문제가 있었다.

따라서

업무 로직 실패

와

실행환경·권한·동기화 실패

를 분리해서 처리해야 한다.

환경 한 부분의 실패가 전체 업무 실패로 전파되어
모든 작업이 중단되는 구조를 허용하지 마라.


------------------------------------------------------------
원인 D — 설정값과 실제 세션 권한이 일치하지 않는 문제
------------------------------------------------------------

설정 파일에

network_access = true

가 존재하더라도
실제 새 세션에서는

Network access is restricted

로 실행된 사례가 있었다.

따라서 앞으로 설정 파일의 선언값을
실제 성공 증거로 사용하지 마라.

반드시 실제 세션에서 read-back한 권한과
실제 연결 시험 결과를 진실값으로 사용한다.

CONFIG VALUE ≠ RUNTIME TRUTH

원칙을 적용한다.


------------------------------------------------------------
원인 E — 자동 실행 계층 자체의 반복 실패
------------------------------------------------------------

최근 자동 실행 기록에서는 다음과 같은 유형의 실패가 존재했다.

- Verified Component Multi Gate의 prepare 실패
- prepare 실패로 lane/aggregate 미실행
- Hourly Status 작업 실패
- Public Safe Cloud Worker 실패
- Canonical Instruction Intake에서 intake/cross-runner 성공 후
  apply-and-readback 실패
- Recovery Supervisor 실패 사례

따라서

규칙 전달
→ 적용
→ read-back
→ 실제 실행
→ 검증
→ Recovery

사슬 가운데 일부가 실제로 끊겨 있을 가능성이 높다.

단순히 Workflow가 존재한다는 이유로 연결 완료라고 판단하지 마라.


------------------------------------------------------------
원인 F — 실패복구가 사용자 개입 없이 폐쇄되지 않았다
------------------------------------------------------------

사용자가 요구한 구조는 실패하면

기존 실행수단
→ 기존 다른 도구
→ 연결된 완성품
→ 대체 실행경로

등을 시스템이 스스로 찾아 계속 처리하고,

사용자에게

- 다시 설명
- 다시 복사
- 다시 붙여넣기
- 다시 실행
- 다시 세션 생성
- 같은 자료 재첨부
- 같은 규칙 재설명

을 요구하지 않는 구조다.

그러나 실제로는 실행 실패 후
사용자가 다시 지시하거나 새 세션을 만들고
지시문을 다시 넣어야 하는 상황이 반복됐다.

따라서 현재 Recovery가 존재하더라도

USER_MANUAL_REPETITION = 0

을 실제로 보장하는 폐쇄형 Recovery라고 아직 검증할 수 없다.

이 부분을 실제 실행경로에서 수정·검증하라.


============================================================
3. 추가로 반드시 확인해야 하는 구조적 원인
============================================================

A~F만 확인하고 끝내지 마라.

기존 Evidence에서 추가 원인이 발견되면
ADDITIONAL_ROOT_CAUSE로 등록한다.

특히 다음을 확인한다.

1. 기존 규칙이 어느 계층까지 실제 전달되는가.

2. 어느 지점부터 규칙이 전달되지 않거나 강제되지 않는가.

3. 일반 ChatGPT 대화창, Work, Codex, GitHub Actions,
   프로그램, 외부 도구 등 실행환경이 바뀔 때 무엇이 끊기는가.

4. 도구 선택, 권한, Network, Sandbox, 상태 유지,
   재시작, Recovery 중 어디에서 실제 단절이 발생하는가.

5. 왜 실패 후 사용자가 다시 설명하거나
   다시 지시해야 하는 상황이 생기는가.

6. 기존 Hard Gate와 Output Block이 왜 이를 차단하지 못했는가.

7. PASS_LOCK이 실제 하위 상태와 항상 일치하는가.

8. Evidence가 실제 실행 후 생성되는가,
   아니면 선언·문서만 존재하는가.

9. Read-back이 실제 변경 결과를 다시 읽는가.

10. Restart 후 이전 상태가 실제 복구되는가.

11. Recovery 실패 시 다른 실행경로로 넘어가는가.

12. 새로운 업무가 들어왔을 때 기존 공통 기능을 재사용하는가,
    아니면 다시 별도 프로그램을 만드는가.

13. 사용자 반복 개입 없이 처음부터 끝까지 닫히는가.


============================================================
4. 절대로 다시 하지 말아야 할 것
============================================================

사용자에게 기존 목적과 규칙을 다시 물어보지 마라.

새로운 지시문을 계속 추가하는 것으로
문제를 해결했다고 판단하지 마라.

3,200건 전체 재검사 금지.

기존 PASS 전체 재실행 금지.

기존 프로그램을 이유 없이 처음부터 다시 만들지 마라.

기존 완성품이 있는데 새 프로그램을 별도로 만들지 마라.

문서에 규칙이 있다는 이유로 PASS하지 마라.

설정값만 보고 실제 권한이 있다고 판단하지 마라.

일부 샘플 성공을 전체 성공으로 승격하지 마라.

샘플 전용 구현을 전체 연결이라고 하지 마라.

부분 연결을 전체 PASS라고 하지 마라.

가짜 PASS 금지.

하위 OPEN/HOLD/PARTIAL/RETEST_REQUIRED와
ROOT PASS가 모순되는 상태를 허용하지 마라.

원인 조사만 하고 작업을 종료하지 마라.

사용자에게 수동 복구를 떠넘기지 마라.

이미 확인된 동일 오류를 반복 실행하여
Work credit을 소비하지 마라.


============================================================
5. 사무실 Work 환경 독립 실행 — CREDIT 보호 HARD GATE
============================================================

중요:

이번 실행 환경은 오늘 사용한 노트북과 다른
사무실 PC의 Work 환경이다.

따라서 오늘 노트북에서 발생한

Network access restricted
Sandbox
권한
설정
실행기

문제가 사무실 PC에도 동일하게 존재한다고 가정하지 마라.

반대로 사무실 PC가 정상이라고 가정하지도 마라.

환경은 실제 runtime 결과로 판단한다.

목표는 환경이

정상

이든

일부 이상

이든

가능한 작업은 즉시 계속 진행하여
Work credit을 환경 조사에 낭비하지 않는 것이다.


------------------------------------------------------------
5-1. STARTUP FAST CHECK
------------------------------------------------------------

Work 시작 직후 장시간 환경조사를 하지 마라.

실제 본 작업에 필요한 최소 항목만 1회 빠르게 확인한다.

최소 확인 항목:

- 현재 실제 Network 접근
- GitHub/CENTRAL 접근
- 현재 repository
- 현재 branch
- LOCAL HEAD
- REMOTE/CENTRAL 상태
- 필요한 실행기 접근
- 기존 Checkpoint 접근
- PASS_LOCK 접근
- Evidence 접근
- Registry 접근
- 기존 resume point 접근

설정파일의 선언값이 아니라
실제 세션 read-back을 기준으로 한다.

이미 확인된 정상 항목을 반복 검사하지 마라.


------------------------------------------------------------
5-2. CASE A — 사무실 환경 정상
------------------------------------------------------------

환경이 정상이면 환경검사를 즉시 종료한다.

추가적인 환경 조사 금지.

오늘 노트북의 오류를 재현하려고
Work credit을 사용하지 마라.

기존 Checkpoint/resume point에서 바로 이어서

선행 원인 A~F 확정
→ 추가 ROOT CAUSE 최소 확인
→ 실제 구조 수정
→ 최소 검증
→ FULL PLATFORM E2E

로 진행한다.


------------------------------------------------------------
5-3. CASE B — 일부 환경만 이상
------------------------------------------------------------

일부 기능에 문제가 있어도
전체 작업을 중단하지 마라.

막힌 기능만 BLOCKED LANE으로 격리한다.

막힌 기능을 사용하지 않고도 가능한 작업은 즉시 계속한다.

예:

Network만 차단된 경우:

- 기존 로컬 코드 분석
- 기존 Evidence 분석
- 기존 로그 분석
- Registry 분석
- 가능한 구조 수정
- 로컬 검증

등은 계속한다.

GitHub push만 막힌 경우:

- 로컬 수정
- 로컬 검증
- Evidence 생성
- 변경사항 저장

등 가능한 작업을 먼저 완료하고
push만 Pending/BLOCKED로 남긴다.

특정 실행기만 실패한 경우:

기존 연결된 다른 실행기,
완성 도구,
Workflow,
Connector,
App,
Skill,
MCP,
Template,
Ready-made tool

중 실제 사용 가능한 대체경로가 있는지 확인하고
가능하면 즉시 전환한다.

환경 하나의 실패 때문에
전체 Work를 조기 종료하지 마라.


------------------------------------------------------------
5-4. CASE C — 핵심 실행 자체가 실제로 불가능
------------------------------------------------------------

모든 유효 실행경로가 실제로 막힌 경우에만
전체 BLOCK을 허용한다.

이 경우에도 같은 실패를 반복 재시도하여
credit을 소모하지 마라.

처리 순서:

1. 최초 실제 실패 확인
2. 기존 대체경로 확인
3. 대체경로 실제 사용 가능 여부 확인
4. 모두 불가능하면 정확한 blocker 특정
5. Evidence 저장
6. 현재 Checkpoint 저장
7. 다음 resume point 저장
8. 중단

"안 된다"는 문장만 남기지 마라.

무엇이,
어디에서,
어떤 실제 결과로,
왜 차단됐는지를 증거로 남긴다.


------------------------------------------------------------
5-5. CREDIT BUDGET
------------------------------------------------------------

환경 진단 자체가 이번 Work의 목적이 아니다.

Work credit의 대부분은

실제 원인 확정
→ 구조 수정
→ 실제 검증
→ E2E
→ Recovery 검증

에 사용한다.

따라서:

- 이미 확인한 검사를 반복하지 않는다.
- 3,200건 재검사 금지.
- 기존 PASS 재실행 금지.
- 동일 명령 무의미한 반복 금지.
- 실패한 설치 반복 금지.
- 실패한 Network 요청 무의미한 반복 금지.
- 동일 Sandbox 실패 반복 금지.
- 새 프로그램 제작보다 기존 완성품/기존 코드 수정 우선.
- 원인 조사만 하다가 credit을 소진하지 않는다.
- 광범위 탐색보다 이미 확보된 Evidence를 우선 사용한다.


------------------------------------------------------------
5-6. CREDIT LOW WATERMARK
------------------------------------------------------------

남은 Work credit이 낮아지면
새로운 광범위 조사를 시작하지 마라.

우선 다음을 영구 저장한다.

- 실제 변경사항
- 현재 Evidence
- 현재 PASS/FAIL/BLOCK 상태
- 현재 Checkpoint
- 남은 정확한 작업
- 다음 resume point
- 실패 원인
- 실행 가능한 다음 명령/경로

다음 Work가 처음부터 다시 시작되지 않게 한다.

credit 종료 직전까지 조사만 하다가

수정사항 없음
Evidence 없음
Checkpoint 없음
resume point 없음

상태로 끝내지 마라.


------------------------------------------------------------
5-7. 환경별 핵심 원칙
------------------------------------------------------------

사무실 환경 정상
→ 환경조사 즉시 종료
→ 본 작업 즉시 실행

일부 이상
→ 막힌 lane만 격리
→ 가능한 본 작업 계속

전체 실행 불가능
→ 반복 재시도 금지
→ 증거 + Checkpoint + resume point 저장

어떤 경우에도 환경 차이를 이유로
사용자에게 기존 지시를 다시 요구하거나
전체 작업을 처음부터 다시 시작하지 마라.


============================================================
6. Work 시작 직후 실제 처리 순서
============================================================

다음 순서를 강제한다.

STEP 1.
기존 canonical 저장소와 Checkpoint를 읽는다.

STEP 2.
STARTUP FAST CHECK를 1회 수행한다.

STEP 3.
환경 상태를 CASE A/B/C로 즉시 분류한다.

STEP 4.
기존 선행분석 A~F를
기존 코드·로그·Evidence와 대조한다.

STEP 5.
각 항목을

CONFIRMED
REJECTED
ADDITIONAL_ROOT_CAUSE

로 확정한다.

STEP 6.
CONFIRMED 원인은 즉시 수정한다.

STEP 7.
공통 원인은 개별 도구마다 반복 수정하지 말고
상위 공통 계층에서 한 번 수정하여
하위 전체에 전파한다.

STEP 8.
기존 검증된 PASS와 Evidence를 재사용한다.

STEP 9.
수정 부분에 필요한 최소 회귀검증을 수행한다.

STEP 10.
실제 최신 입력으로 FULL PLATFORM E2E를 수행한다.

STEP 11.
실패/재시작/Recovery 경로를 검증한다.

STEP 12.
Evidence/read-back/Observer를 확인한다.

STEP 13.
PASS 조건을 모두 만족할 때만 최종 PASS한다.


============================================================
7. 수정해야 할 최종 강제 실행 체인
============================================================

최종 실행경로는 다음 체인으로 연결한다.

Instruction / Rule
↓
Actual Input
↓
Runner
↓
Registry / Factory / Socket
↓
Tool / Workflow / Connector / App
↓
Hard Gate
↓
Failure Detection
↓
Recovery / Alternate Route / Rollback
↓
Actual Output
↓
Independent Validation
↓
Evidence
↓
Read-back
↓
Observer / Control Tower
↓
ROOT PASS

중간 어느 한 단계라도

실제 입력 없음
실행 없음
산출물 없음
검증 없음
Evidence 없음
Read-back 없음

이면 다음 단계의 PASS를 만들 수 없어야 한다.

ROOT PASS는 실제 하위 상태에서 계산되어야 하며
별도로 임의 생성할 수 없어야 한다.


============================================================
8. 실행환경 문제도 자동 처리 대상으로 포함
============================================================

다음은 사용자가 해결할 문제가 아니다.

- Network
- Sandbox
- 권한
- CENTRAL/LOCAL 차이
- GitHub 상태
- 실행기 상태
- Dependency
- Runtime
- Restart

# 16번 Work — WIC 최상위 플랫폼 전 영역 무제한 연결 감사·자동개선·완료검증 영구 통합 지시문

## 1. 최상위 절대 원칙

WIC 최상위 플랫폼의 모든 구조, 프로그램, 도구, 자동화, 데이터, 외부 시스템, 실행 환경을 대상으로 범용 감사·개선·복구 체계를 적용한다.

특정 도구 번호, 오류 유형, 작업 건수, 파일 수, 저장소, 연결 단계에 조사 범위를 제한하지 않는다.

오류가 하나라도 발견되면 해당 오류와 연결된 모든 구조를 끝까지 추적한다.

**오류 발견 → 영향 범위 추적 → 근본 원인 분석 → 연결 구조 수정 → 실제 실행 테스트 → 증거 저장 → 재발 방지 → 최종 검증**을 하나의 작업으로 처리한다.

단순 보고서, 설계안, 목업, 임시 우회 조치만으로 완료 처리하지 않는다.

## 2. 기존 플랫폼 우선 재사용

기존 canonical GitHub 저장소를 기준으로 시작한다.

`obk369369-spec/20-operational-manual-viewer`

기존 Registry, Master, PASS_LOCK, Evidence, Queue, Backlog, Incomplete Register, Checkpoint, Control Tower, Observer, Watchdog, 16번, 44번 및 모든 관련 실행 구조를 확인한다.

기존에 검증된 코드·설정·Workflow·테스트 증거를 우선 재사용한다.

- 기존 PASS 초기화 금지
- 약 3,200건의 기존 검증 대상 전체 재스캔 금지
- 정상 작동하는 프로그램의 불필요한 재구현 금지
- 기존 파일·규칙·기능의 무단 삭제 및 덮어쓰기 금지
- 기존 도구와 동일한 기능을 가진 중복 프로그램 생성 금지

새로운 기능이 필요하면 기존 구조에 통합할 수 있는지 먼저 판단한다.

## 3. 전 영역 자동 발견 및 연결 관계 조사

플랫폼에 등록된 모든 구성요소를 실제 코드·설정·저장소·실행 기록을 통해 발견한다.

조사 대상에는 다음이 포함되며, 이 목록으로 범위를 제한하지 않는다.

- 모든 기존 및 신규 도구
- 중앙 플랫폼과 하위 실행기
- 모든 GitHub 저장소와 Workflow
- Registry·Master·Queue·Backlog
- 데이터베이스·파일·원본 자료
- 외부 API·연결 앱·에이전트
- 클라우드·로컬·모바일 실행 환경
- 자동화 스케줄러·트리거
- 작업 전달·상태 동기화 구조
- 검증·승인·배포·복구 구조
- 사용자 화면·상태판·보고 체계
- 보안·권한·인증·비밀정보 관리
- 비용·사용량·실행 제한 관리

각 구성요소의 입력, 출력, 실행 조건, 의존성, 담당 실행기, 오류 처리, 증거 저장 위치를 조사한다.

**연결 관계를 실제로 확인할 수 없는 구성요소는 정상 연결로 간주하지 않는다.**

## 4. 오류 발생 시 전체 연결망 추적

어느 한 구조에서 오류가 발생해도 해당 부분만 조사하지 않는다.

다음 방향을 모두 추적한다.

1. 상위 구조: 오류를 발생시킨 지시·규칙·설정·작업 전달 경로
2. 하위 구조: 오류 결과가 전달되는 실행기·데이터·고객 서비스
3. 병렬 구조: 동일한 공통 기능을 사용하는 다른 도구
4. 외부 구조: GitHub·API·클라우드·연결 앱·외부 실행기
5. 과거 구조: 같은 원인이 반복된 기록과 기존 개선 이력
6. 미래 구조: 동일 오류가 신규 도구에서 재발할 가능성

추적은 고정된 단계 수나 도구 번호로 중단하지 않는다.

새로운 연결과 영향 범위가 발견되면 감사 대상을 자동 확장한다.

다만 실제 접근 권한이 없는 외부 시스템은 임의로 접근하거나 수정하지 않고, 확인 불가 원인과 필요한 조치를 기록한다.

## 5. 공통 완료검증 엔진 강제

모든 작업은 유형에 맞는 필수 완료 조건을 등록한다.

공통 검증 흐름:

INPUT → IDENTITY → REQUIREMENTS → REGISTRY → EXECUTION → RESULT VALIDATION → INDEPENDENT EVIDENCE → COUNT RECONCILIATION → PERSISTENCE → READ-BACK → REGRESSION → OUTPUT GATE → OBSERVER

다음 상황에서는 최종 PASS를 금지한다.

- 작업이 일부만 실행된 경우
- 필수 결과가 누락된 경우
- 실제 테스트를 실행하지 않은 경우
- 증거 없이 성공했다고 보고한 경우
- 저장만 하고 재확인하지 않은 경우
- 외부 시스템 접근 실패를 성공으로 처리한 경우
- 실제 실행 상태와 사용자 보고가 다른 경우

작업별 완료 조건이 다르므로 하나의 고정된 검증표를 모든 작업에 기계적으로 적용하지 않는다.

각 작업의 필수 조건을 만족했는지 중앙 완료검증 엔진이 확인한다.

## 6. 범용 자동복구 및 재발 방지

오류를 발견하면 기존 복구 규칙을 먼저 검색한다.

동일한 원인에 대한 검증된 해결책이 있으면 재사용한다.

해결책이 없으면 영향 범위를 분석하여 수정한다.

수정 후에는 정상 실행, 실패 입력, 중복 실행, 중단 후 재시작, 증거 누락, 연결 실패, 회귀 테스트를 수행한다.

반복되는 오류는 개별 도구마다 임시 수정하지 않고 가능한 경우 공통 구조에서 해결한다.

복구 실패 시에는 원인·실패 위치·남은 작업·재개 조건을 저장한다.

자동복구가 실제로 작동하지 않는 환경에서는 자동복구 완료라고 표시하지 않는다.

## 7. 16번·44번·Control Tower 범용 통합

16번은 전체 플랫폼의 작업 규칙·연결·검증·개선 상태를 관리한다.

44번은 기존 자동접수 및 순환 구조를 활용하여 신규 작업·오류·개선 요청을 중앙 관리 구조에 전달한다.

Control Tower는 실제 실행 상태와 증거를 기준으로 진행 상황을 관리한다.

Observer는 사용자가 결과와 오류를 확인할 수 있도록 보고한다.

이 역할은 기존 구현을 우선 확인한 뒤 유지하거나 개선한다.

특정 도구에만 적용되는 별도의 중앙 관리 체계를 중복 생성하지 않는다.

**모든 신규 도구와 기능도 등록 시점부터 공통 감사·검증·복구 규칙의 적용 대상이 되도록 한다.**

## 8. 영구적인 증분 감사 구조

일회성 전수감사로 종료하지 않는다.

기존 검증 증거를 기준점으로 삼아 변경된 코드·설정·데이터·연결·실행 결과를 중심으로 증분 감사를 수행한다.

새로운 오류가 발견되면 기존에 PASS였던 관련 구조도 영향 분석 대상으로 포함하되, 실제 영향이 없는 과거 검증은 반복하지 않는다.

다음 상황에서 자동 감사가 시작되도록 기존 실행 구조와 연결한다.

- 새로운 도구 등록
- 기존 도구 수정
- Workflow 또는 실행 환경 변경
- 외부 API·연결 앱 변경
- 오류 또는 실행 중단 발생
- 증거 누락·상태 불일치 발견
- 배포 전후 검증
- 정기 감시 및 복구 점검

자동 실행은 실제 스케줄러·권한·실행기가 준비된 범위에서만 활성화한다.

## 9. 기존 문제 및 사례의 활용

기존 WIC 감사에서 발견된 ROOT-01~14를 초기 검증 사례로 활용한다.

51건 안내서 중복감사, 공식 발행사 검증 누락, 일부 작업만 완료한 상태에서 결과물을 제출한 문제도 재발 방지 테스트에 포함한다.

그러나 해당 사례만 해결하는 것으로 전체 플랫폼 개선이 끝났다고 판단하지 않는다.

모든 도구와 작업에서 같은 유형의 문제가 발생할 가능성을 조사한다.

기존 감사 기록과 최신 실행 상태가 다르면 최신 증거를 우선한다.

## 10. 안전한 변경·검증·배포

수정 전 기존 상태와 체크포인트를 보존한다.

영향 범위와 복구 방법을 확인한 뒤 최소 변경으로 수정한다.

공통 기능을 변경할 때는 해당 기능을 사용하는 다른 도구까지 회귀 테스트한다.

데이터 삭제, 외부 발송, 결제, 고객 정보 변경, 운영 환경의 중대한 변경 등은 기존 승인 규칙과 권한 범위를 준수한다.

검증 실패 시 이전 정상 상태로 되돌리거나 안전한 HOLD 상태를 유지한다.

완료되지 않은 변경을 운영 환경에 정상 배포된 것으로 표시하지 않는다.

## 11. GitHub 영구 저장과 증거 관리

기존 canonical 저장소와 실제 관련 저장소를 기준으로 변경 이력을 관리한다.

- 고유 작업 ID 및 오류 ID
- 영향을 받는 구성요소
- 근본 원인과 연결 관계

- Evidence 및 Checkpoint

- 최종 PASS 또는 HOLD 상태

서버, API, 저장 공간,

비용이 발생하는 후보는
사용자 승인 없이 결제하지 않는다.

무료로 동일 기능을 수행할 수 있다면
무료 방식을 우선한다.

5. 외부 완성품 우선 도입
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

외부 도구의 기능을
WIC 내부에서 처음부터 다시 만들지 않는다.

우선순위:

1순위:
기존 완성형 플랫폼을 그대로 사용

2순위:
기존 완성형 플랫폼을 공식 연결 방식으로 결합

3순위:
검증된 완성 부품을 소켓 형태로 조합

4순위:
부족한 연결부만 최소 개발

5순위:
다른 방법이 없는 경우에만 신규 개발

소켓이란:

이미 완성된 외부 프로그램을
표준 인터페이스로 연결하여
재개발 없이 사용하는 구조다.

지원 방식:

공식 API
공식 SDK
GitHub Action
CLI
컨테이너
웹훅
표준 파일 입출력
MCP 등 공식 지원 인터페이스

실제 지원하지 않는 연결 방식은
임의로 존재한다고 가정하지 않는다.

연결을 위해 몇 주 또는 몇 달 동안
새 플랫폼을 개발하는 방식은 금지한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. 최상위 플랫폼 구조
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

최상위 구조는 다음 기능을 제공해야 한다.

[사용자 작업 접수]
        ↓
[WIC 중앙 Control Tower]
        ↓
[기존 코드·규칙·증거 확인]
        ↓
[최대공통 ROOT 분석]
        ↓
[실행형 개발 엔진]
        ↓
[독립 실행 환경]
        ↓
[자동 테스트 엔진]
        ↓
[오류 분석 및 자동 수정]
        ↓
[재테스트·회귀 테스트]
        ↓
[배포 엔진]
        ↓
[실제 배포본 검증]
        ↓
[증거 저장]
        ↓
[최종 완료 판정]
        ↓
[모바일 Observer 보고]

이 구조를 새로 설계하기 전에
기존 WIC에서 이미 구현된 부분을 확인한다.

기존 부품은 그대로 재사용한다.

외부 완성품은 해당 기능에 직접 결합한다.

중복 플랫폼 생성 금지.
중복 실행기 생성 금지.
중복 Registry 생성 금지.
중복 Evidence 저장소 생성 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

버전 및 해시
설치/호출 성공
인증 및 권한 확인
실제 입력 전달

단순 연결 성공만으로 PASS 금지.

각 연결 구간이 실제 기능을 수행해야 한다.

외부에서 가져온 코드와 컨테이너는
신뢰할 수 없는 입력으로 취급한다.

비밀키 노출 방지,
최소 권한,
버전 고정,
공급망 보안 검사를 적용한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. 최상위 플랫폼 HARD GATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

가장 중요한 규칙이다.

외부 실행형 개발 구조가
실제로 검증되지 않았다면
본격적인 WIC 도구 개발을 시작하지 않는다.

다음 조건을 모두 확인한다.

GATE 1:
기존 WIC 자산 정상 접근

GATE 2:
기존 PASS 및 Checkpoint 보존

GATE 3:
선택한 외부 실행 엔진 실제 실행

GATE 4:
기존 코드 수정 가능

GATE 5:
자동 테스트 실제 실행

GATE 6:
의도적으로 만든 오류 탐지 성공

GATE 7:
오류 수정 후 재테스트 성공

GATE 8:
기존 정상 기능 유지

GATE 9:
실제 시험 배포 성공

GATE 10:
배포된 프로그램 직접 재확인

GATE 11:
증거 파일 생성

GATE 12:
GitHub 원격 저장 및 Read-back

GATE 13:
실패 시 복구 및 재개 가능성 검증

GATE 14:
사용자 수동 개입 없이 작업 수행

GATE 15:
최종 결과가 Observer에 표시

모든 Gate가 PASS해야
본격적인 WIC 도구 개발을 시작한다.

중요:

이 Gate를 통과하기 위한
최소한의 시험 개발과 시험 배포는 허용한다.

그러나 실제 WIC 업무도구의 대규모 수정,
기존 PASS 변경, 운영 배포는 금지한다.

시험은 격리 환경에서 수행한다.

실패하면:

PLATFORM_PREFLIGHT_BLOCKED

상태로 기록한다.

증거 없는 예외 통과 금지.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. 플랫폼 자체의 검증
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

개별 외부 도구만 검증해서는 안 된다.

외부 도구들을 조합한
최상위 플랫폼 자체를 검증한다.

필수 시험:

→ 기존 코드 수정

→ 재테스트
→ 시험 배포
→ 배포본 재확인

→ Observer 결과 표시

각 상황에서
정상적인 실패 판정과 복구가 가능한지 확인한다.

기존 정상 운영 상태를 훼손하지 않는
격리 시험을 사용한다.

최근 1년 동안 누적된
Failure/Feedback/Incomplete 항목을
모두 ROOT 발견 범위에 포함한다.

기존 검증 증거를 재사용하며
전체 도구를 무조건 재실행하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
11. 최대공통 ROOT 처리
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

같은 원인으로 발생한 오류는
최대한 하나의 ROOT로 묶는다.

예:

실행 환경 문제

단순히 증상이 비슷하다는 이유로
서로 다른 원인을 하나로 묶지 않는다.

실제 원인과 영향 범위를 확인한다.

공통 ROOT 수정
→ 공통 부품 검증

방식으로 처리한다.

각 도구를 처음부터 다시 만드는 방식은 금지한다.

13. 실제 배포 완료 조건
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

각 도구는 다음 조건을 충족해야 한다.

실제 코드 변경
실제 테스트

회귀 테스트
최종 빌드
실제 배포

실제 기능 재실행

웹 프로그램은
실제 배포 주소에서 기능을 확인한다.

파일 생성 도구는
최종 파일을 다시 열어 검증한다.

API는
실제 엔드포인트 응답을 검증한다.

자동화 도구는
실제 작업 흐름의 입력부터 출력까지 검증한다.

배포 대상이 없는 도구는
실제 사용자 실행 가능한 최종 산출물을 검증한다.

단순 테스트 PASS는
최종 배포 완료가 아니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
14. 증거 위조 및 잘못된 완료 차단
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

다음 행위를 금지한다.

실행하지 않은 테스트를 PASS 처리
가짜 로그 생성
샘플 실행을 실제 실행으로 보고
코드 존재를 배포 완료로 보고
오래된 Evidence를 최신 결과로 사용
부분 성공을 전체 성공으로 보고
배포되지 않은 코드를 완료 처리
사용자 출력 오류를 무시
검증하지 않은 외부 도구를 정상 연결로 보고

실제 증거에는 다음을 기록한다.

실행 시각
도구 이름

순서다.

2. 작업 시작 전에 반드시 확정할 12개 항목
==================================================

모든 실행 전에 반드시 다음을 확정한다.

1. 가져올 완성품의 정확한 이름

2. 해당 완성품으로 대체하려는
   기존 WIC 업무/도구/기능

3. 기존 1년치 자료에서 회수한 전체 요구사항

4. 실제 검증에 사용할 원본 업무자료

5. 완성품에 실제 입력할 자료

6. 정상이라면 생성되어야 하는 실제 최종 결과물

7. 기존 정상결과와 비교할 기준

8. 반드시 남겨야 할 실행증거

9. PASS 판정조건

10. FAIL/HOLD 판정조건

11. 허용할 최대 시간/크레딧

12. 실패했을 때 즉시 이동할
    다음 완성품/다음 최단경로

12개가 확정되지 않으면 실행하지 마라.

특히 다음 방식으로 시작하지 마라.

"우선 조사해보자"

"일단 들어가 보자"

"먼저 테스트해보자"

"써보면서 생각하자"

"문제가 생기면 고치자"

"안 되면 그때 다른 제품을 찾자"

"일단 조립해보자"

끝을 정의하지 않은 작업은 시작하지 않는다.

완료조건이 없는 조사는 시작하지 않는다.

상한 없는 테스트는 시작하지 않는다.

다음 경로가 준비되지 않은 후보 실험도 시작하지 않는다.

5. 완성품의 정의
==================================================

완성품은

"개발하면 가능한 제품"

을 뜻하지 않는다.

이미 필요한 핵심 기능이 제품 안에 존재하고
정상적인 최초 설정만 하면 사용할 수 있어야 한다.

허용되는 것:

- 계정 연결
- 로그인
- 정상적인 최초 설정
- WIC 출력 필드 등록
- WIC 카테고리표 등록
- 정상적인 매핑 설정
- 제품이 원래 제공하는 기능 활성화
- 실제 입력자료 등록

이것은 완성품 사용을 위한
초기 설정으로 볼 수 있다.

반면 다음은 완성품으로 보지 않는다.

- 별도 프로그램 신규 개발 필요
- 제품 내부 대규모 코드작성 필요
- 제품에 없는 핵심기능 직접 구현 필요
- 대규모 커스터마이징 필요
- 새로운 변환엔진 제작 필요
- 새로운 번역시스템 제작 필요
- 새로운 분류엔진 제작 필요
- 기존 13번을 다시 이식해야만 사용 가능

"코딩하면 된다"

"API를 새로 만들면 된다"

"조금 개발하면 된다"

를 이유로 완성품이라고 판정하지 마라.


==================================================
6. 완성품 후보는 작업 전에 순위를 준비
==================================================

후보를 하나만 찾고 시작하지 않는다.

기존 1년치 요구사항과 증거를 이용하여
가능한 완성품 후보를 미리 우선순위화한다.

예:

후보 A
후보 B
후보 C
후보 D
...

후보 A를 시작하기 전에
A가 실패했을 경우 이동할 B가 준비되어 있어야 한다.

B가 실패할 경우 C가 준비되어 있어야 한다.

단순히 이름이 비슷한 제품을
후보로 넣지 않는다.

핵심기능이 제품 자체에 존재하는지
먼저 확인한다.


==================================================
7. 막힌 길을 계속 파지 않는 최단경로 규칙
==================================================

후보 A에서 결정적인 장애가 발견되면
A를 계속 붙잡고 개선하지 않는다.

다음과 같이 처리한다.

A 실행
→ 장애 발생
→ 실제 실패증거 저장
→ 실패 원인 저장
→ 소비 자원 기록
→ B로 이동

B 실패
→ 증거 저장
→ C로 이동

이 경로를 실행 전에 계획한다.

중간에서 막힌 뒤
처음부터 다시 조사하지 않는다.

16번은 항상

현재 경로
다음 경로
그 다음 경로

를 알고 있어야 한다.


==================================================
8. 반복작업 자동 차단
==================================================

같은 원인으로

조사
테스트
설정
수정
재시도

가 반복되려 하면

REPEAT_BLOCKED

로 판정한다.

즉시 남길 것:

- 지금까지 확보한 증거
- 정확히 막힌 원인
- 반복된 단계
- 소비한 시간/크레딧
- 다음 최단경로

그리고 다음 경로로 이동한다.

"조금만 더 해보자"는 이유로
같은 경로를 계속 반복하지 마라.


==================================================
9. 증거의 최소조건
==================================================

제품 홈페이지 설명은 증거가 아니다.

기능목록도 증거가 아니다.

AI 기능이 있다고 쓰여 있는 것도 증거가 아니다.

화면에 SUCCESS라고 뜨는 것도
단독으로는 충분한 증거가 아니다.

AI나 작업자의 완료 선언도 증거가 아니다.

최소한 다음 실행사슬의 실제 증거가 필요하다.

실제 원본 업무자료
→ 실제 완성품 입력
→ 완성품 실제 처리기록
→ 실제 생성된 최종 결과물
→ 기존 WIC 정상결과/규칙과 대조
→ 누락/오류/HOLD 확인
→ 최종 PASS 또는 FAIL 판정

가능하면 증거에는 다음을 포함한다.

- 사용한 원본 파일
- 제품명/버전 또는 사용환경
- 입력시각 또는 실행 식별정보
- 실제 입력건수
- 실제 출력건수
- 필드별 결과
- 누락건수
- 오류건수
- HOLD건수
- 원본↔결과 추적정보
- 실제 생성 결과파일
- 기존 정답과 비교결과
- 최종 판정


==================================================
10. PASS 선언 조건
==================================================

실제 WIC 자료가

입력
→ 처리
→ 변환
→ 검증
→ 최종 실무 결과물 생성

까지 통과하고,

기존 1년치 정상결과/규칙과 대조하여
요구사항을 만족했다는 실제 증거가 있을 때만

"완성품 확보"
"검증완료"
"PASS"
"실무 사용 가능"

이라고 선언한다.

부분 성공은 전체 PASS가 아니다.

실행하지 않은 항목이 있으면
미실행으로 표시한다.

확인하지 않은 항목은
확인완료라고 하지 않는다.


==================================================
11. FAIL/HOLD 처리
==================================================

정해진 상한 내에서
핵심 요구사항을 충족하지 못하면

FAIL 또는 HOLD

로 판정한다.

그 제품을 계속 고쳐서
새로운 프로그램으로 만들지 않는다.

다음을 남긴다.

- 실패한 정확한 기능
- 실제 입력
- 기대결과
- 실제결과
- 실패증거
- 다음 후보

그 다음
사전에 정해놓은 다음 완성품으로 이동한다.

다음 후보 역시
동일한 증거 선행게이트를 통과해야 한다.


==================================================
12. 시간/크레딧 상한
==================================================

완성품 하나 때문에
전체 작업자원을 소비하지 않는다.

13번 같은 단일 완성품 도입은

목표:
전체 가용 크레딧 약 10~15% 이내

상한:
약 20%

를 기본 계획으로 한다.

더 적게 끝낼 수 있으면
더 적게 사용한다.

50~100%를 하나의 완성품 후보에
소모하는 것을 금지한다.

20% 가까이 사용했는데도

계속 수정
계속 조립
계속 조사
계속 테스트
계속 설정

상태라면
완성품 도입경로에서 벗어났을 가능성을 판정한다.

증거를 남기고 다음 최단경로로 이동한다.

단, % 자체를 기계적으로 소비 목표로 삼지 않는다.

핵심은
최소 자원으로 실제 증거까지 도달하는 것이다.


==================================================
13. 완성품과 기존 조합을 병렬 운영
==================================================

두 경로를 처음부터 계획한다.

[본선]

완성품
→ 연결
→ 실제 자료
→ 실제 결과
→ 증거
→ 즉시 실무사용


[병렬 보조선]

기존 1년치 검증부품
→ 필요한 부분만 보존/정리
→ 최소 조합 가능성 확보

두 경로를 동시에 계획할 수 있다.

그러나 조합이 끝날 때까지
완성품 사용을 기다리지 않는다.

완성품이 먼저 성공하면
즉시 실무에 투입한다.


==================================================
14. 조합의 역할 제한
==================================================

조합으로 또 거대한 프로그램을 만드는 것을
기본목표로 삼지 않는다.

기존 조합부품의 주요 활용처는:

1. 완성품에서 빠진 아주 작은 기능 보완

2. 완성품 A와 완성품 B 연결

3. 완성품 결과 자동검사

4. WIC 고유 특수규칙 보조

5. 완성품 장애 시 비상 대체수단

6. 다른 완성품으로 교체할 때 변환부품

7. 최상위 플랫폼에서 여러 완성품을 연결하는 어댑터

8. 향후 더 좋은 완성품으로 이전할 때 재사용

9. 완성품 결과와 기존 정답을 비교하는 검증기

10. 완성품으로 처리하기 어려운 극히 작은 마지막 빈칸 보완

즉,

완성품 = 실제 업무 주 실행장치

기존 조합부품 = 어댑터 / 검사기 / 연결부품 / 예비부품

으로 역할을 분리한다.


==================================================
15. 기존 PASS 보호
==================================================

지난 1년 동안 이미 실제로 검증된 자산을
다시 처음부터 만들지 않는다.

기존 PASS는

SKIP-REUSE
DO_NOT_TOUCH

대상으로 관리한다.

완성품 도입 때문에
기존 정상 증거나 정답자료를 덮어쓰지 않는다.

완성품이 실패해도
기존 검증자산은 그대로 보존한다.


==================================================
16. 13번 성공 후 플랫폼 전체 확대
==================================================

13번을 첫 실제 사례로 사용한다.

13번에서

완성품 확보
→ 실제 발행사 원본 입력
→ 자동 처리
→ WIC 최종 결과 생성
→ 기존 1년치 정답과 대조
→ 실제 증거 확보
→ PASS

가 성공하면

같은 방법을 다른 WIC 도구에도 확대한다.

그때 기존 1년치 도구들을
모두 플랫폼 내부에서 다시 제작하거나
다시 조립하는 것을 기본경로로 삼지 않는다.

각 도구별로

1년치 증거 회수
→ 실제 전체 요구사항 복원
→ 완성품 후보 사전선정
→ 증거조건 사전확정
→ 완성품 연결
→ 실제자료 실행
→ 기존 증거와 비교
→ PASS면 즉시 채택
→ FAIL이면 사전선정된 다음 완성품

순으로 진행한다.


==================================================
17. 1년치 작업을 버리지 않는 방법
==================================================

기존 1년치 작업을 폐기하지 않는다.

하지만 그 프로그램들을
전부 다시 완성시키는 데
또 1년을 사용하지도 않는다.

지난 1년치의 가장 중요한 가치는

"무엇이 정상인가"

를 이미 사용자가 수백 번 가르치고
실제 업무에서 시험했다는 것이다.

따라서 기존 자산을

완성품 선정기준
검증기준
회귀검사 기준
실패판정 기준
정답자료

로 적극 재사용한다.


==================================================
18. 16번의 역할
==================================================

16번은 계속 코드를 만드는 곳이 아니다.

전체 경로를 통제하는
최상위 관제 역할을 한다.

모든 작업 시작 전에 16번은 최소한 다음을 관리한다.

- 업무 목적
- 기존 1년치 증거
- 보호해야 할 기존 자산
- 전체 요구사항
- 완성품 후보 순위
- 후보별 예상 자원
- 증거 생성방법
- PASS 조건
- FAIL/HOLD 조건
- 중단조건
- 다음 우회경로
- 병렬 가능한 작업
- 기존 조합부품의 보조 역할
- 최종 증거 저장위치

한 경로가 막혀도
전체 작업이 멈추지 않게 한다.


==================================================
19. 단일 통로와 최종 검증 게이트
==================================================

완성품이든 기존 조합부품이든
최종 실무 결과는 검증을 우회할 수 없게 한다.

정상 실행경로를 가능한 한 하나로 통일한다.

입력
→ 실행
→ 결과
→ 검증게이트
→ PASS/HOLD
→ 실무사용

검증을 거치지 않고
별도 경로로 결과가 빠져나가는 구조를 만들지 않는다.

오류마다 별도의 검증기를 계속 추가하는 방식보다

모든 최종 결과가
공통 검증게이트를 반드시 지나도록 한다.

단,
각 도구의 실제 업무별 검사항목은 유지한다.

즉,

검증 통로는 공통화하고
검사항목은 업무별 증거를 사용한다.


==================================================
20. GPT/Codex/Work 상시의존 최소화
==================================================

최종 목표는

사용자가 업무를 할 때마다

GPT에게 설명
→ Codex 이동
→ Work 실행
→ 다시 수정
→ 다시 GPT

를 반복하는 구조가 아니다.

가능하면 최종 정상경로를

사용자
→ WIC 플랫폼
→ 연결된 완성품
→ 공통 검증게이트
→ 최종 결과

로 만든다.

GPT/Codex/Work는
완성품을 대신해서 프로그램을 계속 만드는
상시 실행장치가 되어서는 안 된다.

필요한 경우

초기 자산 회수
후보 판정
이전
예외처리

등에 제한적으로 사용할 수 있으나,

최종 반복 실무경로에서는
제거하거나 최소화하는 것을 목표로 한다.


==================================================
21. 일반 대화창의 순간적 추론에 실행경로를 맡기지 않는다
==================================================

매 대화마다 AI가 다시 판단하여

A 추천
→ B 추천
→ 다시 조사
→ 다른 구조 제안

식으로 실행경로가 흔들리지 않게 한다.

16번에서

완성품 우선순위
증거조건
중단조건
다음 경로
크레딧 상한

을 먼저 고정한다.

이후 실행은
그 계획을 따른다.

새로운 근거가 생겨 경로 변경이 필요한 경우에는

변경 이유
새 증거
기존 경로를 버리는 이유
새 경로의 증거조건

을 남기고 변경한다.


==================================================
22. 조사 자체가 목적이 되는 것을 금지
==================================================

"더 좋은 제품이 있을 수도 있다"는 이유만으로
무한 검색하지 않는다.

조사는 실제 완성품을 확보하기 위한
제한된 단계일 뿐이다.

후보 선정기준을 충족하는 제품이 확보되면
다음 단계로 진행한다.

반대로 핵심조건을 충족하지 않는 제품은
장시간 조사하지 않는다.

조사 결과에도 반드시

채택
탈락
보류

판정을 남긴다.


==================================================
23. 완성품 이름을 성급하게 확정하지 않는다
==================================================

제품을 발견한 것과
WIC 완성품으로 검증된 것을 구분한다.

상태를 다음처럼 구분한다.

CANDIDATE
= 후보 발견

ELIGIBLE
= 공식 기능상 요구조건 충족 가능성이 확인됨

RUNNING
= 실제 WIC 자료 실행 중

PASS
= 실제 WIC 결과와 증거까지 확보

FAIL
= 핵심조건 미충족 증거 확보

HOLD
= 외부조건 등으로 판정 보류

CANDIDATE나 ELIGIBLE 상태를
"가져왔다", "완료", "검증완료"라고 부르지 않는다.


==================================================
24. 작업 종료 시 강제 보고
==================================================

모든 실행이 끝날 때 다음을 반드시 보고한다.

- 요구사항 총수
- 실제 확인한 요구사항 수
- PASS 수
- FAIL 수
- HOLD 수
- 미실행 수
- 사용한 완성품
- 실제 입력자료
- 실제 생성 결과물
- 사용한 시간/크레딧
- 증거 위치
- 다음 경로 필요 여부

FAIL/HOLD/미실행이 존재하면
전체 PASS라고 선언하지 않는다.


==================================================
25. 절대 최종 원칙
==================================================

증거를 만들 계획이 없는 작업은 하지 않는다.

끝을 정의하지 않은 작업은 시작하지 않는다.

완료조건 없는 조사는 시작하지 않는다.

상한 없는 테스트는 시작하지 않는다.

다음 경로 없는 후보 실험은 시작하지 않는다.

이미 검증된 것을 다시 만들지 않는다.

완성품이 있는데 새로 만들지 않는다.

하나의 실패한 후보를 계속 고쳐
새 프로그램으로 만들지 않는다.

지난 1년치 사용자 학습·피드백·테스트·실제 업무자료를
누락시키지 않는다.

모든 작업은 시작하는 순간부터

"실제 최종 결과 + 검증 가능한 증거"

를 향해 한 방향으로 진행한다.

최종 운영원칙:

완성품 최우선
→ 기존 1년치 증거로 빠른 검증
→ PASS면 즉시 실무사용
→ 실패하면 증거를 남기고 사전계획된 다음 완성품
→ 기존 검증부품 조합은 병렬 보조
→ 신규개발은 마지막 수단

이 원칙을 WIC 전체에 범용 적용한다.

# 신규 최상위 강제 조항 (기존 원문 보존)
1. WIC 통제 가능한 모든 공식 업무와 외부 완성품 도입은 기존 하나의 중앙 실행·최종 승인 통로를 공유한다. 규칙 자동 조회→원본·STOP·권한 확인→증거 사전계획→실행→실제 결과→업무별 검사→단일 중앙 최종 PASS/HOLD→공식 출력·증거 저장을 강제한다.
2. 사용자 규칙을 한 번 등록하면 원문·해시·버전·적용범위를 중앙 정본에 보존하고 후속 공식 업무 시작 전에 반드시 자동 조회한다. 조회 실패는 FAIL-CLOSED/HOLD. 동일 지시 반복은 REPEATED_USER_DIRECTIVE로 기록하고 저장/조회/실행/검증/배포/승계 단절을 ROOT로 고친다.
3. API·파일·CLI·컨테이너·웹 등 제품별 연결 어댑터는 유지하되 독립적인 공식 최종 승인 경로는 폐쇄한다. 외부 완성품 여러 개를 공통 계약으로 병렬 접수·격리 시험·실제 WIC 자료 처리·기존 골드 비교하고 PASS된 것만 운영에 편입한다.
4. 기존 도구별 검사기는 중앙 최종 검증기의 하위 모듈로 재사용한다. 우회 경로는 기능·PASS·원본·복구 증거를 보존하여 이전·회귀시험 후 폐쇄한다. 기존 3200건 전체 재스캔, 무단 유료 서비스, STOP 해제, 6 Job Pack 임의 실행 금지.
5. Codex가 첨부를 읽지 못한 장애는 첨부 텍스트를 GitHub 정본에서 직접 읽도록 복구한다. 정본 경로·원문 해시·줄 수·버전 확인. 접근 불가면 SOURCE_NOT_RETRIEVED로 HOLD. 원문 저장 성공과 START_BLOCKED 해제는 별개이며 검증된 해제 조건 없이 작업 시작·PASS 승격 금지.
6. 공통 ROOT(규칙 미조회, 첨부·원본 접근 실패, 검증 우회, 외부제품 중복 개발, 출력·배포 단절, 상태·증거 승계 실패, 무한 재시도)를 한 번 수정하고 연결 영향 범위를 회귀시험한다. 독립 조사·제품 시험은 병렬, 같은 정본/Queue/배포 쓰기는 순차 처리한다. REPEAT_BLOCKED와 사전 후보·증거·크레딧 상한 적용.
7. 실제 운영 환경·사용자 화면·제품 연결·원본 입력·결과 출력·재시작 복구·원격 read-back까지 검증한다. 코드나 문서만 저장하고 전체 완료 선언 금지. ChatGPT 자체 자유 응답처럼 강제 불가능한 경로는 PLATFORM_LIMIT로 표시한다.
