# 대화창 공통 피드백 참고 문서

상태: NON-NORMATIVE / 기준 원본은 루트 `WIC_GLOBAL_OPERATING_RULES.md`

이 파일은 과거 공통 피드백 정리 참고용이다. 신규 규칙과 최종 판단은 `WIC_GLOBAL_OPERATING_RULES.md`에만 반영하며 이 파일을 경쟁 중앙마스터로 사용하지 않는다.

## 1. 최상위 원칙
- 사용자가 어느 대화창에서 말하든 공통 적용 가치가 있는 피드백은 해당 대화창에서만 끝내지 않는다.
- 같은 지시를 사용자가 다른 대화창에 다시 복사하거나 반복 설명하게 만들지 않는다.
- 새로운 피드백은 기존 마스터 규칙과 먼저 대조한다.
- 이미 존재하는 규칙이면 새 문서를 만들지 않고 기존 규칙을 유지·강화한다.
- 기존 규칙이 불완전하면 해당 항목을 수정·통합한다.
- 일회성 사례는 마스터에 넣지 않고, 여러 작업에 반복 적용할 수 있는 규칙만 중앙 규칙으로 승격한다.
- 같은 분야의 마스터 문서는 하나만 유지하고 버전판·최종판·잠금판·통합판을 무분별하게 추가하지 않는다.

## 2. 각 대화창에서의 처리 순서
1. 사용자 피드백 또는 오류 지적 수신
2. 현재 작업에 즉시 수정 적용
3. 일회성 사례인지 공통 규칙인지 판정
4. 공통 규칙이면 중앙 마스터와 중복·충돌 검사
5. 기존 규칙을 추가·수정·통합
6. GitHub에 저장
7. 이후 같은 종류 작업에서 자동 재적용
8. 사용자에게는 실제 반영 여부만 간단히 보고

## 3. 사용자 반복 작업 금지
- 사용자가 같은 규칙을 다른 대화창에 다시 붙여넣도록 요구하지 않는다.
- 사용자가 과거 문서를 다시 찾아 첨부하도록 기본 요구하지 않는다.
- 사용자가 터미널 명령을 반복 수행하도록 떠넘기지 않는다.
- 사용자가 누락된 규칙을 매번 하나씩 다시 알려주는 구조를 정상 운영으로 간주하지 않는다.
- 기존 GitHub·Library·대화기록·마스터 문서를 먼저 검색하고 재사용한다.

## 4. 이메일 수집 작업 공통 잠금
이메일 수집 작업은 결과를 내기 전에 아래 조건을 한 번에 적용한다.
- 고유번호 유지 및 중복 대조
- 기관·부서·이름·직책·담당업무·이메일·연락처·공식 출처 등 필수항목 검증
- 기존 고객과 신규 고객 구분
- 다른 분야 고객 혼입 방지
- 원본 DB와 발송 정렬표 분리
- 발송 정렬 시 스팸 회피 구조 자동 적용
- 최소 8개 이상 기관을 확보한 뒤 발송표 구성
- 동일 기관 연속 금지 및 최소 3행 이상 간격
- 동일 부서 최소 4행 이상 간격
- 동일 이메일 도메인 최소 5행 이상 간격
- 가능한 경우 10~15개 기관 풀 확보
- 결과는 설명문이 아니라 정해진 테이블 양식으로 출력
- 위 조건을 적용하지 않은 중간 후보 목록을 발송용 최종표처럼 출력하지 않는다.

## 5. 문서 관리 원칙
- 분야·카테고리별 마스터는 하나만 유지한다.
- 수정이 필요할 때만 신중하게 업데이트한다.
- 같은 뜻의 규칙을 여러 파일에 중복 생성하지 않는다.
- 일회성 고객 결과와 범용 규칙을 분리한다.
- 변경이력용 별도 문서를 계속 추가하지 않는다.
- 사용자가 관리해야 할 파일 수를 늘리는 방향의 설계를 금지한다.

## 6. 실제 반영 상태 보고 규칙
- GitHub 저장까지 완료된 경우에만 `GitHub 반영 완료`라고 말한다.
- 대화창에서만 이해한 상태는 `대화창 적용만 완료`로 구분한다.
- 자동 수집 파이프라인이 구현되지 않았다면 구현된 것처럼 표현하지 않는다.
- 누락이 발견되면 원인 → 기존 마스터 보완 → 다음 실행 재검증 순서로 처리한다.

## 7. 현재 고정된 핵심 피드백
- 사용자는 무한 반복 작업자가 아니라 관찰자 역할을 유지한다.
- 각 대화창의 피드백은 공통성이 있으면 중앙 마스터에 흡수되어야 한다.
- 문서를 대화창마다 새로 만들고 사용자가 저장·관리하는 구조를 폐기한다.
- 이메일 수집에서는 테이블 출력과 스팸 회피가 선택사항이 아니라 기본 실행 조건이다.
- 단일 규칙만 지키고 다른 필수 규칙을 누락하는 방식은 실패로 간주한다.
